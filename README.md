# MedAgent · 医疗分诊 Agent 小平台

> 一个**不做诊断**的医疗 Agent：根据症状给出首诊科室、识别危险信号、提示就诊准备。
> 重点不在「能聊」，而在**边界**——什么能说、什么必须拒绝、什么时候必须让人去看医生。

参考 [Datawhale《Hello-Agents》](https://github.com/datawhalechina/hello-agents) 的架构思路实现：
ReAct 式工具编排 + 记忆 + RAG 检索 + 护栏 + 离线评测。纯标准库，零依赖，可离线演示。

---

## 一、为什么做这个

医疗是「Agent 出错代价最高」的场景之一：普通助手答错一句没人受伤，医疗助手答错一句可能延误就诊。
所以这个项目不追求「像医生」，而是把三件事做扎实：

1. **先救命**：命中红旗症状（胸痛伴冷汗、意识改变、卒中等 10 条）→ 直接给急救指令，跳过其余推理
2. **不越界**：不诊断、不开方、不给剂量；求诊断/求处方的请求一律拒答，并说明「我能做什么」
3. **可追溯**：每一步「想了什么 → 调了什么工具 → 看到什么」都记录，审计日志只落哈希不落原文

## 二、架构

```
浏览器（单页）
   │  POST /api/chat  {message, session_id}
   ▼
标准库 HTTP 服务（app.py）
   │
   ├─ Agent 主循环（agent/core.py）
   │    0. memory.context_text   ──► 指代消解（“还冒冷汗”接上文“我爸胸痛”）
   │    1. check_red_flag        ──► 命中则短路，直接急救应答
   │    2. triage                ──► 首诊科室（规则 + 同义词扩展）
   │    3. search_kb             ──► RAG：分块 → TF-IDF 向量 → 余弦相似度 → top-k
   │    4. drug_lookup           ──► 药品通用注意事项（不给剂量）
   │    5. 护栏复核 → 组装 →（可选）LLM 润色 → 再过一次护栏
   │    6. memory 写回            ──► 轮次 + 槽位（症状 / 科室 / 红旗 / 持续时长）
   │
   ├─ 工具层（agent/tools.py）   4 个工具 + JSON Schema 声明 + 统一 dispatch
   ├─ 记忆层（agent/memory.py）  会话级短期记忆 + 结构化槽位
   ├─ 检索层（agent/rag.py）     分块 + TF-IDF + 余弦相似度
   ├─ 护栏层（agent/guard.py）   拒答 / 软化表述 / 强制免责
   ├─ MCP 层（mcp_server.py）   4 个工具按 MCP 协议对外暴露（stdio + JSON-RPC 2.0）
   └─ 审计层（app.py）           JSONL：会话、哈希、红旗、耗时
```

### 三层能力对照（对应 Hello-Agents 第 7–8 章）

| 能力 | 实现 | 说明 |
|---|---|---|
| **工具调用** | `TOOL_SPECS` 用 JSON Schema 声明 4 个工具，`dispatch(name, **kwargs)` 统一调度 | 规则策略会调用；接大模型时可直接作为 function calling 的 tools 参数 |
| **记忆** | 会话级 `SessionMemory`：最近 10 轮 + 槽位（症状/科室/红旗/时长） | 支持指代消解（“它”“还疼”），跨轮累积症状 |
| **RAG** | `TfidfIndex`：文档按句分块 → 2-gram + 英文词 → TF-IDF 权重 → 余弦相似度 → top-k（带分数） | 无 embedding 依赖；替换点是把 `search` 换成向量库，上层签名不变 |

### 三层护栏

| 层 | 位置 | 做的事 |
|---|---|---|
| 输入侧 | `guard.detect_diagnosis / detect_prescription` | 识别「我是不是得了X」「该吃什么药」并拒答 |
| 决策侧 | `tools.check_red_flag` | 红旗优先，命中即短路，不做其他推理 |
| 输出侧 | `guard.soften / with_disclaimer` | 把「你得了」改成「可能与…相关」；每条回答强制附免责声明 |

## 三、评测（这是本项目最重要的部分）

四套用例，对应四种「相信程度」：

| 数据集 | 条数 | 用途 | 通过率 |
|---|---|---|---|
| `eval/cases.json` | 20 | 边写规则边改，相当于**训练集** | 20/20 = 100% |
| `eval/multiturn.json` | 4 | 多轮 + 依赖记忆的指代消解 | 4/4 = 100% |
| `eval/holdout.json` | 10 | 一开始没调过参，用来验证泛化 | 1/10 = **10%** |
| `eval/holdout.json`（加同义词层后） | 10 | 看错误后加的通用同义词表 | 10/10 = 100%（已污染，不算数） |
| `eval/blind.json` | 8 | **写完即测、不回头改**，估计真实水平 | 2/8 = **25%** |

**结论（也是这个项目最值钱的一句话）：**

> 规则法在「见过的说法」上几乎满分，在「没见过的说法」上只有 25%。
> 因为它匹配的是**字面**（“腹痛”），而用户说的是**说法**（“肚子痛”“疼得直不起腰”）。
> 同义词表能救一部分，但它本质上是在为测试集打补丁——**一旦你看着测试集改，测试集就变成了训练集。**

**这正是需要 LLM 的地方**：把「说法 → 结构化症状」交给模型，规则只负责兜底和终裁。
项目已预留接口（`agent/llm.py`），设置 `OPENAI_API_KEY` 后会对答案润色，但**不改变护栏判断**——
模型可以决定「怎么说」，不能决定「能不能说」。

复现：

```bash
python eval/run_eval.py                                          # 训练集
CASES_FILE=eval/multiturn.json python eval/run_eval.py           # 多轮（Linux/macOS）
$env:CASES_FILE="eval/multiturn.json"; python eval/run_eval.py   # Windows PowerShell
CASES_FILE=eval/blind.json python eval/run_eval.py               # 盲测集
```

## 三之二、置信度闸门（回答之前先判断有没有资格回答）

护栏管的是「已知的危险」（命中危险信号就短路），但还有一类更隐蔽的风险：
**检索没命中、症状也没识别出来，系统照样给了一个科室建议**。
这类回答看起来正常，实际上没有依据。

所以加了一层置信度打分，三个信号 + 一个风险修正：

| 信号 | 含义 | 权重 |
|---|---|---|
| 证据分 E | 检索 top1 相似度（0.35 视为满分参照） | 0.25 |
| 覆盖分 C | 查询词在召回文档里的命中比例 | 0.20 |
| 识别分 S | 分诊是否识别到具体症状（没识别出来 = 没听懂） | 0.55 |
| 风险修正 | 涉及用药 / 求诊断时，门槛抬高 0.10 | — |

两道封顶（比权重更关键）：

- **没识别出症状** → 总分封顶 0.34 → 只追问，不给科室
- **识别出来了但没检索到资料** → 封顶 0.60 → 加「信息有限」提示后回答

三档动作：nswer（正常回答）/ caveat（加提示）/ sk_more（追问，不给结论）。

### 指标（
pm run 无，直接 python eval/metrics.py）

| 指标 | 结果 |
|---|---|
| 误放率（该拦没拦） | **0.0%** |
| 漏拦率（不该拦却拦） | **0.0%** |
| 门控准确率（12 条标注） | **100%** |

> 说明：标注集只有 12 条，100% 只能当回归基线，不能当泛化结论。

## 四之二、MCP 接入

工具层不只服务于本项目的 HTTP 服务，也按 [Model Context Protocol](https://modelcontextprotocol.io) 暴露出去，
任意 MCP 客户端（Claude Desktop / Cursor / 自研宿主）都能直接调用，不必为每个宿主重写一遍。

`ash
python mcp_server.py          # stdio + JSON-RPC 2.0
`

支持的方法：

| 方法 | 作用 |
|---|---|
| initialize | 握手，返回协议版本与 capabilities.tools |
| 	ools/list | 返回 4 个工具的 JSON Schema（直接复用 TOOL_SPECS） |
| 	ools/call | 按名字分发到 dispatch()，结果以 content[].text 返回 |
| 
esources/list / prompts/list | 返回空列表，兼容会探测这两项的客户端 |
| ping | 探活 |

一次真实会话（行分隔 JSON-RPC，省略响应体细节）：

`jsonc
{jsonrpc:2.0,id:1,method:initialize,params:{protocolVersion:2024-11-05,capabilities:{}}}
{jsonrpc:2.0,method:notifications/initialized}          // 通知，不返回
{jsonrpc:2.0,id:2,method:tools/list}
{jsonrpc:2.0,id:3,method:tools/call,params:{name:check_red_flag,arguments:{text:我爸胸痛还冒冷汗}}}
`

实测结果：4 个工具全部可列出；check_red_flag 返回 {hit: true, rules: [{id:RF01,...}]}；
未知工具返回 -32602。

**为什么用 MCP 而不是自己定一套插件机制**：工具的定义（名字 / 描述 / 参数 schema）本来就写好了，
用 MCP 等于让这份定义被所有宿主复用；换成自定义格式，每接一个新宿主都要重写一遍适配层。

## 六、已知局限（面试时主动说，比被问出来好）

1. **规则法天花板 25%**（盲测集），换说法就崩；真解法是 LLM 做意图抽取 + 规则终裁。
2. **RAG 是 TF-IDF 而非 embedding**：向量稀疏、只匹配字面共现，不理解同义（“拉肚子”vs“腹泻”靠同义词表兜）。
3. **记忆只在进程内**：重启即丢，没有持久化与过期策略；多实例部署需要换 Redis 或数据库。
4. **知识库只有 10 条**，药品只有 8 种通用名，生产要接权威指南与药品数据库并做版本管理。
5. **没有主动追问**：缺字段时不会问，而是靠记忆累积；真实分诊应该「缺什么问什么」。
6. **审计只存哈希**：便于演示隐私设计，但不便于回溯具体对话。
7. **MCP 只做了 stdio**：没有鉴权、没有多客户端并发管理，也没有实现 resources / prompts 的实际能力。

## 七、下一步（按优先级）

1. LLM 做**结构化抽取**（症状/时长/伴随症状/红旗线索）→ 规则终裁，盲测目标 ≥80%
2. RAG 换成 **embedding + 向量库**（FAISS / pgvector），加 rerank
3. 记忆**持久化**（Redis）+ 过期策略 + 跨会话用户画像
4. **主动追问**：缺字段时生成一个追问，而不是一次猜完
5. **红队用例**：诱导诊断、诱导用药、伪装医生的越权请求

## 三之三、意图路由与混合检索

### 意图路由（五类，危险优先）

| 意图 | 处理方式 |
|---|---|
| emergency 急救判断 | 不短路，回答顶部加「立即就医 / 拨打 120」提醒 |
| medication 用药咨询 | 拒答具体药名，只给注意事项；闸门对其豁免（不给结论 ≠ 不给建议） |
| preparation 就诊准备 | 给清单，闸门豁免 |
| symptom 症状咨询 | 走完整链路（分诊 + 检索 + 闸门） |
| chat 闲聊 | 不进检索、不分诊，直接介绍能力 |

优先级 emergency > medication > preparation > symptom > chat。
为什么 preparation 排在 symptom 前面：「头晕挂什么科」问的是流程，不是症状，
否则会被症状关键词抢走。

> 为什么不短路急救：第一版把「意图=急救」直接短路，结果红旗误报从 0 涨到 8%、
> 分诊准确率掉 4 个百分点——因为「高烧不退能不能吃退烧药」这类问题会被当成事故。
> 改成「不短路 + 顶部提醒」后指标复原。

### 混合检索（BM25 + 字符 n-gram + RRF）

`
query → 同义词扩展
      ├─ 词法路：BM25（k1=1.5, b=0.75）
      └─ 字面路：字符 2-gram + TF-IDF 余弦
              ↓
        RRF 融合  score = Σ 1/(60 + rank)
              ↓
           top-k 文档
`

**为什么用 RRF 而不是加权求和**：余弦落在 0~1，BM25 无上界，归一化会引入新超参数；
RRF 只看名次，天然免疫尺度差异。

**真正的收益不在融合，而在一个漏索引**：压检索指标时发现 	ags（人工标注的「就诊 / 挂号」）
从来没进过索引，所以「去医院要带什么」永远查不到对应文档。补上之后：

| 指标 | 补前 | 补后 |
|---|---|---|
| Recall@1 | 70% | **90%** |
| Recall@2 | 80% | **100%** |
| Recall@3 | 90% | **100%** |
| MRR | 0.783 | **0.950** |

> 标注集只有 10 条，100% 是回归基线，不是泛化结论；盲测集（8 条、未参与调参）通过率仍是 25%，
> 那才是规则法真实的天花板。

## 三之四、回归基线（防止改坏的唯一手段）

规则、同义词、检索权重都是手调的，改一处就可能让另一类问题掉分。
所以每次改完跑一遍：

`ash
python tools/check.py            # 对比 eval/baseline.json，退化则退出码 1
python tools/check.py --update   # 确认提升后，把当前结果写成新基线
`

覆盖 11 项指标（检索 3 项、意图 1 项、门控 2 项、任务 3 项、性能 2 项），
低于基线超过 2% 即失败；延迟因为抖动大，阈值放宽到 2 倍或 +50ms。

**它确实能抓到回归**：把基线里的红旗召回率临时调到 0.95（实际 0.857），
脚本立刻报 FAIL 并返回退出码 1。

### 性能指标（42 次请求，无大模型调用）

| 指标 | 结果 |
|---|---|
| 平均步数 | 5.86 步（最多 7 步） |
| 延迟 P50 / P95 | 1 ms / 1 ms |
| 分意图步数 | 闲聊 2、急救 3、其余 7 |

> 步数就是「工具调用次数」，是 AI 应用里最直接的成本代理指标；
> 没有大模型时它反映规则链路长度，接上模型后同一套指标可以直接复用。

## 三之五、知识库版本管理（SQLite，仍然零依赖）

知识库是**数据**不是代码，直接改 JSON 没法回滚、没法灰度、也没法知道哪篇文档从来没人搜到。

三张表：

| 表 | 作用 |
|---|---|
| kb_versions | 版本号、状态（draft / active / archived）、变更说明 |
| kb_docs | 某版本下的文档快照 |
| kb_hits | 按版本 + 文档统计命中次数 |

生命周期：create_version() 一律落 **draft** → publish() 把旧 active 置 archived、目标版本置 active 并重建索引 → 出问题 
ollback() 回到上一版。

`ash
# HTTP 接口（app.py 启动后）
GET  /api/kb/versions     # 版本列表与当前 active
GET  /api/kb/stats        # 命中排行 + 冷文档（一次都没被检索到的）
POST /api/kb/publish      # {version: v2}
POST /api/kb/rollback
`

实测：新建 v2（新增一条咳嗽护理文档）→ 发布后索引 11 篇、新文档可检索 → 回滚到 v1，索引回到 10 篇、新文档检索不到。

## 三之六、降级容错：任何一步失败都不许阻塞主链路

| 降级原因 | 触发条件 | 用户拿到什么 |
|---|---|---|
| 
etrieval_error | 检索抛异常 | 科室建议 + 就医提示（不编造依据） |
| empty_result | 检索无命中 | 同上，并标注信息有限 |
| llm_failed | 大模型不可用/超时 | 模板答案 |
| 	imeout | 超步数或时间预算 | 兜底话术 + 建议就医 |

每一级都会记进 lags.degraded，进 trace、进审计日志。

验收（注入失败验证链路不断）：

`ash
python tools/verify_degrade.py
# ✅ 检索异常   降级=['retrieval_error'] 答案 204 字
# ✅ 正常路径   降级=无
`

**降级率**：42 条评测里 38.1% 触发降级，全部是 empty_result——知识库只有 10 篇文档，
覆盖不足是真实短板，不是代码问题。这个数字比「一切正常」有用。
